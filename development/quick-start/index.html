Quick start

  1. Initialize the child pipelines and shared Boutros Lab modules:

bash git submodule update --init --recursive

  1. Prepare the mzML input CSV, a target-decoy FASTA, and the MSFragger JAR. If selecting ProtLoom, also prepare a ProtLoom project YAML with the same FASTA and accession markers as the run configuration.

  2. Copy config/template.config to a run-specific file. Set input_csv, decoy_database, msfragger_executable, output_dir, and dataset_id. Set validate_ProteomicPSM.protloom_project_yaml when using ProtLoom. Review the shared markers and the child-specific settings for your experiment. Keep the template's includeConfig lines and final methods.setup() call.

  3. Run with Nextflow 24.10.6 and its v1 syntax parser. Choose a work directory with enough space for the mzML files and child pipeline work:

bash export NXF_VER=24.10.6 export NXF_SYNTAX_PARSER=v1 export NXF_WORK=/scratch/$SLURM_JOB_ID/metapipeline-ProteomicDIA-work nextflow run main.nf -c /path/to/run.config -profile pines

The scratch path above is an example for a Slurm job; use another suitable work directory outside Slurm. Select -profile pines for a 64 CPU, 500 GB node or -profile boutroslab_aws for a 32 CPU, 128 GB node. These profiles set resource budgets, while child_profile (standard by default) selects the container runtime in each child. Make sure the selected child profile's runtime is available. Nextflow's -c option adds the run configuration to the project's configuration; see the Nextflow configuration documentation.

Resource profiles

Profile Node budget Parent launch processes Child allocations
pines 64 CPUs, 500 GB 2 CPUs, 4 GB per child launcher MSFragger search 8 CPUs/64 GB; iProphet 8 CPUs/32 GB; DIA-NN 16 CPUs/96 GB; QC DIA-NN report 2 CPUs/32 GB.
boutroslab_aws 32 CPUs, 128 GB 2 CPUs, 4 GB per child launcher MSFragger search 8 CPUs/64 GB; iProphet 8 CPUs/32 GB; DIA-NN 16 CPUs/96 GB; QC DIA-NN report 2 CPUs/16 GB.

Parent CSV, QC manifest, and configuration tasks request 1 CPU and 2 GB in both profiles. Parent child-launch processes request 2 CPUs and 4 GB from config/resources.json. Each profile has its own file under config/resource_profiles, containing its budget and CPU requests for every child process. A process memory value is optional: omit it to leave that child's Nextflow memory directive unset. search_database_MSFragger is the exception because it uses task.memory to size the Java heap. The profile's max_memory remains required as a node budget. The parent passes process requests through each child's parameter JSON and a small resource override config, including qc-ProteomicDIA. Existing child resource defaults remain in effect when neither profile is selected. A run config can set base_resource_update within a child namespace to replace that profile's process requests. These profiles describe node budgets; they do not select a Slurm partition or change the local executor.

For a profile outside the repository, copy pines.json or boutroslab_aws.json to a directory you control, rename it <name>.json, and edit its budget and allocations. Set these values in your run config:

params.compute_profile = 'my_cluster'
params.additional_resource_profile_dir = '/path/to/resource_profiles'

Run with -c /path/to/run.config; a matching Nextflow -profile entry is not required. additional_resource_profile_dir can contain multiple directories separated by the operating system's PATH separator (: on Linux/macOS). Lookup checks those directories from left to right, then the bundled config/resource_profiles directory. Missing directories or missing files in one location are skipped. Relative directories resolve from the launch directory. A profile file found earlier takes precedence over a file of the same name found later. To add a bundled profile, add its name to config/profiles.config and create config/resource_profiles/<name>.json. The shared parent process requests usually do not need to change.
